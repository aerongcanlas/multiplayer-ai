# Shared-room API

Fastify owns desktop room authorization and business logic. It queries the existing
Supabase PostgreSQL tables using parameterized SQL. It does not invoke
`desktop_room_snapshot`, `desktop_room_command`, or `desktop_save_generated_suggestions`.
SQLite remains the host-local execution/recovery journal. Web routes and desktop tab
read-along RPCs retain their existing transports; the API snapshot includes shared tabs.

## Run locally

1. Apply the complete ordered [database migration chain](../../supabase/README.md),
   including the tab read-along migration. Existing deployments must reconcile migration
   history first. This change does not apply migrations or deploy a service.
2. Copy `.env.example` to `.env` here and set the Supabase URL, public publishable key,
   and server-only PostgreSQL connection string for that same project. The database
   role needs access to `auth.users` (identity/profile/email reads), the room tables,
   `desktop_prompt_suggestion`, and `desktop_tab_share`, with RLS bypass. Keep these
   credentials on the backend. Use certificate-verified TLS for remote PostgreSQL;
   do not disable certificate verification.
3. On Windows, run `pnpm dev:shared` from the repository root in Command Prompt
   (cmd). It starts both the API and desktop and sets `MP_API_URL` to
   `http://127.0.0.1:3001`; keep `PORT=3001` in the API's `.env`. Keep the terminal
   open and press Ctrl+C to stop both. The separate `pnpm dev:api` and
   `pnpm dev:desktop` commands remain available for independent development.
4. For a packaged desktop, set `apiUrl` in `apps/desktop/config/supabase.json` to the
   deployed HTTPS API origin before building. Its empty default produces an explicit
   setup-required state for shared rooms. Development accepts a loopback HTTP origin;
   packaged builds ignore the environment override and require HTTPS.

Production entry point: `pnpm --filter @multiplayer-ai/api build` then
`pnpm --filter @multiplayer-ai/api start`. Bind `HOST` as required by the hosting service
and terminate HTTPS there. Browser integration/CORS is outside this desktop migration.

## HTTP contract

Every request uses `Authorization: Bearer <Supabase access token>`. The API verifies it
with Supabase Auth; it never accepts client-provided authors or user IDs. Responses are
`Cache-Control: no-store`. Mutations return `{ roomId, snapshot }`; invite creation also
returns the raw `token` once. Only its SHA-256 hash is stored, with a 24-hour expiration.
Create operations return 201; reads, invitation acceptance, and edits return 200.

| Method | Path                                          | JSON body                                                                                      |
| ------ | --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| GET    | `/v1/rooms/snapshot`                          | none                                                                                           |
| POST   | `/v1/rooms`                                   | `{ name }` (1-80 characters)                                                                   |
| POST   | `/v1/rooms/:roomId/invites`                   | none or `{}`; admin only                                                                       |
| POST   | `/v1/invites/accept`                          | `{ token }`                                                                                    |
| POST   | `/v1/rooms/:roomId/messages`                  | `{ text }` (1-2,000 characters)                                                                |
| POST   | `/v1/rooms/:roomId/suggestions`               | `{ messageIds, prompts }` (1-100 distinct IDs, 1-3 generated prompts, each 1-2,000 characters) |
| PATCH  | `/v1/rooms/:roomId/suggestions/:suggestionId` | `{ prompt, expectedRevision }` (1-8,000 characters; author/admin only)                         |

Prompts are still generated by the local context agent. The API atomically saves its
output and reloads canonical source attribution. Mutations hold membership locks until
commit; invites and suggestion edits use row locks. The write and returned snapshot
share one transaction and one pooled connection. No failed write is automatically retried.
Snapshots retain the latest 200 messages and 50 suggestions per room.

Errors return `{ code, message }`: 400 for invalid input/invites, 401 for invalid sessions,
403 for denied membership/ownership, 404 for missing suggestions, 409 for consumed invites
or stale revisions, and 503 for unavailable dependencies or missing schema. Refresh before
retrying an operation whose response was lost. Existing SQL functions remain available
for older clients; removing them requires a separate compatibility rollout.

## Verify

`pnpm --filter @multiplayer-ai/api test` exercises actual routes against the canonical
migrations in PGlite, with a loopback Auth server. It covers actor isolation, input
validation, invitation rules, generated drafts, canonical attribution, rollback, revision
conflicts, tab metadata, and compatibility with the old snapshot format.

`pnpm test:desktop:e2e` builds the API and desktop, then runs the Electron workflows.
The shared workflow exercises all seven Fastify routes and asserts zero legacy room RPC
calls. Auth and read-along remain local fixtures. PGlite serializes connection leases;
these checks do not validate production PostgreSQL network/TLS or concurrent row locking.
